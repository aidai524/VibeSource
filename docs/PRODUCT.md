# Product definition

## One-line definition

一个专门展示 AI 原生开源产品的 Product Hunt：帮助开发者获得流量，让用户能够体验、验证并复用真实实现。

## Problem

软件开发能力越来越容易获得，但优质产品仍缺少可信的发现渠道与初始流量。普通产品目录容易混入闭源套壳、夸大宣传、不可访问 Demo 和无法验证的数据；用户即使发现产品，也常常无法判断实现方式、许可证和二次开发成本。

## Target users

- Primary user — 开源 AI 产品开发者：需要首发曝光、真实用户、反馈和持续分发。
- Primary user — 技术型发现者与复用者：希望体验产品、审阅源码、评估许可证并部署或二次开发。
- Secondary user — 需要部署、定制、支持或商业授权的团队。
- Editorial operator — 负责核验资格、策划发布、采访开发者和组织内容分发。

## Desired outcome

用户在一个产品页内能够：

1. 直接访问真实 Demo、在线服务或可执行的部署路径；
2. 打开公开源码仓库并看到许可证、技术栈和复用说明；
3. 了解 AI 在开发过程和产品能力中的参与方式；
4. 区分平台抓取、平台核验、开发者自述和付费推广信息；
5. 通过榜单、分类、互动和 Newsletter 发现值得尝试的产品。

开发者能够提交一个符合资格的产品，经人工审核后获得可追踪的发布和分发入口。

## Trust and eligibility rules

- **必须公开源码**：提交可访问的公开仓库；可接受许可证范围仍待确认。公开仓库但未声明许可证时不得自动声称“可自由复用”。
- **必须可体验**：至少提供可访问 Demo、在线服务，或经过核验的可部署说明。
- **必须说明 AI 参与**：产品需声明 AI 如何参与开发，以及 AI 是否构成产品核心能力；最终分类字段仍待确认。
- **必须支持复用判断**：展示技术栈、部署方式、许可证和二次开发说明；缺失项必须明确显示。
- **数据必须有出处**：GitHub Star、Fork、Commit 等显示来源与抓取时间；活跃用户、收入等显示为自述、附证据或未验证。
- **必须人工审核发布**：自动检查只提供证据，不替代编辑判断。
- **商业曝光必须透明**：赞助位与自然榜单视觉和数据逻辑分离，并明确标注。

## Core user paths

### Developer submission

1. 开发者填写产品资料、公开仓库、体验入口、AI 参与说明和复用信息。
2. 系统检查必填项并读取可验证的 GitHub 元数据；失败和缺失项保持可见。
3. 提交进入待审核状态，不自动公开。
4. 编辑人工检查源码、体验入口、许可证和宣传内容。
5. 通过后发布产品页，并进入符合条件的分类和榜单计算。

### Product discovery

1. 用户从每日榜单、分类或 Newsletter 进入产品页。
2. 用户比较 Demo、源码、AI 参与方式、技术栈、许可证和指标出处。
3. 用户访问产品、查看源码、点赞或评论；登录和反作弊策略待确认。
4. 平台记录可解释的分发与互动数据，向开发者提供真实反馈。

## MVP scope

- 产品提交与草稿/待审核状态。
- 公开 GitHub 仓库检查和可验证元数据快照。
- 编辑后台或受控审核流程。
- 产品详情页与 Demo、源码、AI 参与、技术栈、部署、许可证和复用信息。
- 每日榜单、分类页和明确版本化的排序规则。
- 点赞和评论；身份、限频与治理策略待确认。
- Newsletter 明示订阅、退订和人工确认发送。
- 50–100 个经过人工筛选和核验的首发产品。
- 基础来源标记、错误状态、重试和审核记录。

## Business model sequencing

在自然发现和首批真实流量形成后，按以下顺序小规模验证：

1. 透明标注的付费置顶与首发服务；
2. 产品介绍整理、Demo、视频、发布内容与跨平台人工代运营；
3. 流量分析、反馈、候补名单、更新日志和邮件触达订阅工具；
4. 部署、定制、技术支持和商业授权等开源产品复用市场。

代码开源不等于服务免费。任何收费请求都必须在发生前展示服务范围、价格和外部影响，并由用户确认。

## Explicit non-goals for the first release

- 不做无需公开源码的普通产品目录。
- 不保证产品质量、流量、收入或安全性。
- 不把开发者自述伪装成平台核验数据。
- 不用虚构产品、指标、评价或不可用按钮填充页面。
- 不自动发布产品、自动发送营销邮件或自动购买推广。
- 不让付费曝光改变未标注的自然榜单结果。
- 不在 MVP 内建设完整的多平台代运营系统、开发者 SaaS 套件或交易市场。
- 不因“未来可能扩展”提前采用多仓库 federated 协作结构。

## Human-control guardrails

- 产品上线、下架、赞助内容、付费请求、Newsletter 发送、外部消息、权限变更和数据删除必须保持可见且可确认。
- 管理员覆盖自动检查时必须记录理由。
- 删除优先采用可恢复的软删除或归档；永久删除策略待确认。
- 外部指标失败或过期时显示状态，不使用静默回退的伪造值。

## Early operating model

- 前期至少一半精力投入产品寻找、开发者采访、内容制作和真实用户分发。
- 正式开放社区提交前，人工建立 50–100 个高质量首发产品。
- 网站能力与内容供给同步推进；首发成功不能只用“功能上线”衡量。

## Initial success signals

- 首发库存：50–100 个已人工核验产品。
- 供给质量：公开仓库、体验入口和必填复用信息的合格率。
- 发现价值：产品页到 Demo、源码和部署说明的有效点击。
- 开发者价值：从发布获得的访问、反馈和可归因用户。
- 社区健康：有效点赞/评论与垃圾、刷量比例。
- Newsletter：明示订阅、打开与点击；具体目标待确认。

## Open questions

- VibeSource 是否作为对外品牌名，首发语言和目标市场是什么？
- 哪些许可证被视为合格开源，双许可证和无许可证仓库如何处理？
- AI 参与程度采用单一标签还是“开发过程”和“产品能力”两个维度？
- 技术栈、数据库、托管、对象存储和观测方案是什么？
- 使用何种登录方式，GitHub 使用 OAuth、GitHub App 还是公开 API？
- 点赞、评论、每日榜单的规则、时区、反作弊和申诉机制是什么？
- Newsletter、分析和后续支付供应商是什么？
- 哪些活跃用户或收入证据允许显示“已核验”，证据保存多久？
